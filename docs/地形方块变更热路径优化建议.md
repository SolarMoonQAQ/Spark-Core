# 地形方块变更热路径优化建议

> 状态：建议（未实施）
> 适用版本：本仓库当前 HEAD
> 适用场景：任何在单个 tick 内摧毁/放置大量方块的调用方（爆炸、大规模破坏类技能、地形编辑指令）
>
> **本文自包含**：全部调用链、代码坐标与判据在文内给出，可独立阅读与实施。

***

## 一、要解决的问题

地形刚体与 MC 方块数据的一致性依赖一条同步链：方块变更 → `ServerLevelMixin` → `PhysicsChunkManager#onBlockUpdated` → 脏 section 集合 → 物理步前的 `updateDirtySections` → `PhysicsChunkSection#startAsyncUpdate` 重建该 section 的碰撞形状。

这条链在**逐方块变更**的场景下（玩家挖一块、放一块）成本可以忽略，其设计取向也是这个。但当调用方在**一个 tick 内摧毁成千上万方块**时，链上每一层的成本都随方块数线性增长，而其中**真正需要的工作只随受影响的 section 数增长**。

本文要做的是指出这个错配，并给出分级优化候选。**注意：`updateDirtySections` 这一层已经做了 section 去重**——同一 tick 内一个 section 无论被改多少方块，重建只发生一次。错配发生在它**上游的逐方块记账**。这个区分决定了优化的落点：不需要动重建逻辑，需要动的是「每个方块都跑一遍」的那几段。

***

## 二、调用链与成本分布

```text
（调用方）在一 tick 内摧毁 N 个方块
  └─ 每个方块一次 Level#setBlock → Level#markAndNotifyBlock
       └─ Level#onBlockStateChange(pos, old, new)                    // 无条件调用，不在任何 flag 分支里
            └─ ServerLevelMixin#onBlockStateChange                   // 本仓库
                 │   早退：old 与 new 均为 isCollisionShapeFullBlock 时不进
                 └─ PhysicsChunkManager#onBlockUpdated(Set.of(pos))  // 每方块一次调用，集合恒为单元素
                      ├─ SectionPos.of(pos) / ChunkPos(pos)          // 每方块分配
                      ├─ markDirtySections(sectionPos)               // 写入 ConcurrentSet，已有去重
                      ├─ chunkHeightIndex.updateSection(...)         // 每方块一次 section 重扫 ★
                      └─ submitDeduplicatedTask(
                             "terrain_update_activate_${blockPos.toShortString()}", …)  // 每方块一次字符串构建 ★
                           └─ contactTest(activator)                  // native，每方块一次
```

标记为 ★ 的两项是本文的主要目标。

### 2.1 `ChunkHeightIndex#updateSection` 的逐方块重扫

```kotlin
// physics/terrain/ChunkHeightIndex.kt
fun updateSection(chunkPos: ChunkPos, chunk: LevelChunk, level: Level, sectionY: Int) {
    ...
    val nowHasSolid = sectionHasSolidBlock(chunk, level, sectionY)   // ← 一次 16³ 扫描
    ...
}
```

`sectionHasSolidBlock` 逐格读取，最坏 4096 次：

```kotlin
// 同文件
private fun sectionHasSolidBlock(chunk: LevelChunk, level: Level, secY: Int): Boolean {
    ...
    if (section.hasOnlyAir()) return false                          // 调色板预检，纯空气直接跳过
    val baseY = secY shl 4
    for (y in 0 until 16) {
        for (x in 0 until 16) {
            for (z in 0 until 16) {
                val state = chunk.getBlockState(BlockPos(x, baseY + y, z))   // ← 每次循环 new 一个 BlockPos
                if (BlockCollisionUtil.hasCollision(state)) return true      // 早期退出
            }
        }
    }
    return false
}
```

三点观察：

1. **答案的单调性**：在一次「摧毁」风暴中，一个 section 的 `sectionHasSolidBlock` 只能从 `true` 翻到 `false`，不会反向翻回（除非同一 tick 内还有放置，见 §四的注意事项）。翻成 `false` 之后，后续每一次 `updateSection` 仍然会完整重扫一遍才得出同一个 `false`。
2. **逐格 `BlockPos` 分配**：4096 次循环每次 `new BlockPos(...)`。`BlockPos` 会经虚调用传给 `chunk.getBlockState`，逃逸分析能否消除这些分配**未经实测**，不应作为主要收益主张；但改成复用一个 `MutableBlockPos` 是零风险的。
3. **`hasCollision` 本身不贵**：`BlockCollisionUtil.hasCollision` 已经按 `Block` 做了 `ConcurrentHashMap` 缓存（`util/BlockCollisionUtil.java`，`COLLISION_CACHE`），底层读的是静态的 `Block.hasCollision`。因此这一层的成本主要在循环与区块读取，不在缓存查找。

> `section.hasOnlyAir()` 的预检已经覆盖了「下界空洞区 / 高空空区」，**完全被挖空的 section** 因此几乎免费。真正贵的是**部分被填满的 section**——正是爆炸坑壁所在的那一层。

### 2.2 `PhysicsChunkManager#onBlockUpdated` 的逐方块记账

```kotlin
// physics/terrain/PhysicsChunkManager.kt
fun onBlockUpdated(blockPositions: Set<BlockPos>) {
    val dirtySections = mutableSetOf<SectionPos>()
    val chunkAffectedSections = mutableMapOf<ChunkPos, MutableSet<Int>>()
    blockPositions.forEach { blockPos ->
        val sectionPos = SectionPos.of(blockPos)
        dirtySections.add(sectionPos)
        val chunkPos = ChunkPos(blockPos)
        chunkAffectedSections.getOrPut(chunkPos) { mutableSetOf() }.add(sectionPos.y())

        physicsLevel.submitDeduplicatedTask("terrain_update_activate_${blockPos.toShortString()}", PPhase.ALL) {
            activator.setPhysicsLocationDp(blockPos.toVec3().add(0.5, 0.5, 0.5).toVec3d())
            physicsLevel.world.contactTest(activator, this)
        }
    }
    markDirtySections(dirtySections)

    for ((chunkPos, sectionYs) in chunkAffectedSections) {
        val mcChunk = mcLoadedChunks[chunkPos] ?: continue
        for (sectionY in sectionYs) {
            chunkHeightIndex.updateSection(chunkPos, mcChunk, physicsLevel.mcLevel, sectionY)
        }
    }
}
```

按 N 个方块计，逐方块发生的是：

- `SectionPos.of` / `ChunkPos` 两个对象构造；
- `ConcurrentHashMap` 的 `getOrPut` + `mutableSetOf`（每方块一次）;
- **`"terrain_update_activate_${blockPos.toShortString()}"`——一次字符串插值 + 一次 `BlockPos.toShortString()` 格式化**，仅用于做去重键；
- 一次 `submitDeduplicatedTask` 写 `taskMap`（`ConcurrentHashMap<PPhase, ConcurrentHashMap<String, () -> Unit>>`，`util/TaskSubmitOffice.kt`）；
- 该任务在后续处理时执行一次 **native `contactTest`**。

其中字符串格式化是明确的浪费：该 key 的唯一用途是去重，而**每个方块的 key 天然不同，去重永远不命中**——每方块都是新键。

### 2.3 `startAsyncUpdate` 的整节重建（已按 section 去重）

```kotlin
// physics/terrain/PhysicsChunkManager.kt
fun updateDirtySections() {
    if (dirtySections.isEmpty()) return
    val sectionsToUpdate = dirtySections.toSet()
    dirtySections.clear()
    if (!physicsLevel.mcLevel.isClientSide && sectionsToUpdate.isNotEmpty()) {
        PacketDistributor.sendToPlayersInDimension(
            physicsLevel.mcLevel as ServerLevel,
            TerrainUpdatePayload(sectionsToUpdate)
        )
    }
    sectionsToUpdate.forEach { sectionPos -> … physicsSection.startAsyncUpdate(this) }
}
```

**这一层是正确的**：`dirtySections` 是集合，同一 tick 内同一 section 只重建一次；重建本身在 `terrainBuilderScope` 线程池上异步执行（`PhysicsChunkSection#startAsyncUpdate`），主线程只付提交成本。§五的候选**不动这一层**。

### 2.4 量级

设一次爆炸在一 tick 内摧毁 `N ≈ 300` 个方块，波及 `S ≈ 40` 个 section：

| 项 | 每 tick 次数 | 每次的量级 |
| --- | --- | --- |
| §2.2 逐方块记账 | `N` | 2 次对象构造 + 1 次字符串格式化 + 1 次 map 写入 + 1 次 native `contactTest` |
| §2.1 `updateSection` | 最坏 `N`（每方块都调一次） | 最多 4096 次区块读取 + 4096 次 `BlockPos` 分配 |
| §2.3 整节重建 | `S` | 4096 格快照 + 逐格 `getCollisionShape`（异步线程） |

**§2.1 是三者中最大的一项**，因为它是 `N × 4096` 量级，而 §2.2 是 `N`、§2.3 是 `S × 4096`。把 §2.1 从「每方块一次」压到「每 section 每 tick 一次」，量级即从 `N × 4096` 降到 `S × 4096`。

## 三、优化候选

### S0 — `sectionHasSolidBlock` 复用 `MutableBlockPos`（零风险）

把循环内的 `BlockPos(x, baseY + y, z)` 换成一个在方法内复用的 `MutableBlockPos`：

```kotlin
private val scratchPos = MutableBlockPos()      // 或作为参数传入

for (y in 0 until 16) {
    for (x in 0 until 16) {
        for (z in 0 until 16) {
            val state = chunk.getBlockState(scratchPos.set(x, baseY + y, z))
            if (BlockCollisionUtil.hasCollision(state)) return true
        }
    }
}
```

**前提与安全性**：`chunk.getBlockState` 不得保留该引用。`LevelChunk#getBlockState` 是即时读取，不存储传入的 `BlockPos`。`scratchPos` 必须是**方法局部或调用线程独占**的字段——不可为跨线程共享的静态字段，因为 `ChunkHeightIndex` 的读取侧在物理线程（见 §四）。

**收益**：消除最坏 4096 次对象分配。**该收益未经实测**，JIT 的标量替换可能已经消除了一部分；实施时应以 §五的口径验证。

### S1 — `updateSection` 的单调性早退（低风险，收益最大）

`updateSection` 只在「section 的有/无实体方块状态翻转」时才需要修改区间表；状态未翻转时它做完全部扫描后原样返回：

```kotlin
if (nowHasSolid == wasSolid) return  // 状态无变化，无需任何操作
```

在一次摧毁风暴中，同一个 section 会被 `updateSection` 调用多次，而绝大多数调用的结论都是「仍然有实体方块（`true == true`，直接返回）」或「已经很早就是空的（`false == false`，直接返回）」。**这两种情形都要先付一次 16³ 扫描才知道。**

可行的省法有两类，**都需要谨慎**：

**(a) 缓存每 section 的「是否为空」结论，只在摧毁/放置真的可能翻转它时才重扫。**
放置与摧毁的语义不同：摧毁只会让 section 变空，因此「已知为空」的结论对摧毁是稳定的；而任何一次放置都可能让空的 section 重新变满。若缓存要正确，就必须在放置路径上无条件失效该缓存。

**(b) 由摧毁方显式告知「该 section 是否已被清空」。**
摧毁方（爆炸）在清空一个 section 时是知道这件事的，但当前接口没有传递这个信息。

**建议**：S1 不要做成「无条件的全量缓存」，而是做成 **(a) 的保守版**——只缓存「为空」这一个方向的结论，并**在所有 `Level#setBlock` 非空气的路径上失效**。失效点可以挂在 `ServerLevelMixin` 上（它已经拦到了 `onBlockStateChange`，且 `newState` 参数直接给出了新状态是否为空）。这样：

- 摧毁风暴：section 一旦变空，后续 `updateSection` 调用都直接返回，不做重扫；
- 放置：`newState` 非空 → 失效缓存 → 恢复完整扫描，正确性不受影响。

**这条是本文收益最大的候选，同时也是唯一有正确性风险的候选**（缓存失效点漏一处就会让高度索引长期停留在错误的「空」结论上，且不报错——它只影响物理线程的地形查询）。实施前应确认 `Level#setBlock` 的所有入口都经过 `onBlockStateChange`：由 §二的调用链可知它确实是无条件调用，因此挂在 `ServerLevelMixin` 上是可靠的。

### S2 — 逐方块记账降为逐 section 记账（需要一个批量入口）

§2.2 里逐方块的三件事——`contactTest` 激活查询、字符串 key、`updateSection`——**都只需要 section 粒度**：

- `updateSection` 的入参本来就是 `(chunkPos, sectionY)`，对同一 section 的 N 个方块调用 N 次与调用 1 次**语义完全相同**；
- `contactTest` 的用途是「这个位置附近有没有刚体，有则激活该 section 的地形」——用一个代表点做一次即可，不需要每方块一次；
- 字符串 key 的构造可以完全去掉。

因此建议**新增一个批量入口**，并让 `onBlockUpdated` 退化为它的单元素调用：

```kotlin
/**
 * 批量版本：一 tick 内的大量方块变更一次提交。
 * 与逐方块调用等价，但以 section 为粒度记账。
 */
fun onBlocksUpdated(blockPositions: Collection<BlockPos>) { … }
```

关键性质：**爆炸侧（或任何调用方）已经在内存里持有完整的变更集合**，但它们拿不到「方块变更 → 地形脏标记」这条链的控制权——`ServerLevelMixin` 是唯一入口，而它每次只收到一个 `pos`。要让批量入口真正被用上，需要二选一：

1. **由 `ServerLevelMixin` 侧聚合**：把同一 tick 内收到的位置攒起来，在 tick 末（或物理步前）一次性提交。这需要确认 `onBlockStateChange` 的调用点都发生在可预期的相位内。
2. **给调用方一条显式通道**：例如一个「开始/结束大批量变更」的作用域，作用域内 `ServerLevelMixin` 只记账不逐条提交。爆炸系统可直接使用（其 `ExplosionInstance#execute` 天然是一批）。

**建议取 2**：它把「批量」变成调用方的显式意图，不依赖对第三方模组变更时机的假设。**这是一个跨仓库接口，需要与调用方（Machine-Max 的爆炸系统）协商后落地。**

### S3 — 去掉热路径上的调试字符串（零风险）

无论是否做 S2，这一条都可以独立实施：

```kotlin
// 本仓库当前形态
physicsLevel.submitDeduplicatedTask("terrain_update_activate_${blockPos.toShortString()}", PPhase.ALL) { … }
```

`toShortString()` 是调试格式化，出现在逐方块热路径上。若 S2 暂不实施，至少应换成不需要格式化的键，例如 `blockPos.asLong()` 的数值拼接或按 section 聚合后的 `SectionPos` 键。

### S4 — `contactTest` 的调用频率（需要澄清语义后决定）

`contactTest` 是 native 调用，本仓库当前的调用频率是每方块一次。要降到每 section 一次，需要先确认激活判据的语义：

- 若判据是「这个 section 里有没有刚体」→ 每 section 一次即可，代表点取 section 中心；
- 若判据是「这个方块附近有没有刚体」（例如刚体恰好只与某一格重叠）→ 需要更细的粒度，或用 section 的 AABB 查询代替点查询。

**本文不臆测该语义**。请在实施 S2/S4 前先确认 `activator` 的掩码与 `contactTest` 结果的处理分支所依赖的粒度。

## 四、正确性约束（不可违反）

1. **`intervals` 的写入必须替换整个 `ShortArray` 引用，不得原地修改。**
   类的文档已明确规定（`ChunkHeightIndex` 类注释：「写入时替换整个 ShortArray 引用，严禁原地修改数组内容」），原因是物理线程在无锁读取 `intervals`。S1 的任何缓存方案都不得破坏这条。

2. **缓存/复用的状态必须区分线程归属。**
   `ChunkHeightIndex` 的写入在主线程，读取在物理线程。S0 的 `MutableBlockPos` 与 S1 的缓存都必须是主线程独占的。

3. **不要在摧毁路径上做「无条件相信调用方」的假设。**
   S1 的失效点必须挂在 `Level#setBlock` 的路径上（`ServerLevelMixin#onBlockStateChange` 同时给出了 `blockState`（旧）与 `newState`（新）两个参数，足以判定方向），而不是假设「摧毁方总会通知我们」。

4. **地形 syncing 的触发点是 `Level#onBlockStateChange`，它不受 `setBlock` 的 flags 影响。**
   这一条对上游调用方是重要的：把 `flags` 调小**不会**减少地形侧的工作，只会丢掉邻居更新与客户端方块包。若上游为了性能想调小 flags，应当被告知这一点。

5. **不要用「整体替换 `LevelChunkSection` 对象」的方式批量清空方块。**
   某些调用方（例如为了吞吐而直接构造新的空 section 对象）会跳过 `Level#setBlock` 整条路径，从而**不触发 `onBlockStateChange`**，地形碰撞体会停留在旧形状上——不报错、不崩溃，只在物理上表现为「坑挖了但撞得到地面」。若确实需要这条路，调用方必须自行按 `SectionPos` 调 `markDirtySections` 补齐同步。

## 五、测量口径

在实施前先取数，否则无法判断 S0–S4 的收益：

| 量 | 位置 | 口径 |
| --- | --- | --- |
| `onBlockUpdated` 调用次数 / tick | `PhysicsChunkManager#onBlockUpdated` | 进入时累加 `blockPositions.size()` |
| `updateSection` 单次耗时 | `ChunkHeightIndex#updateSection` | `System.nanoTime()` 包住，按调用次数累计并按 P99 输出 |
| `updateSection` 中「状态未翻转」的比例 | 同上 | 统计 `nowHasSolid == wasSolid` 早退的命中率——**这个比例直接决定 S1 的收益上限** |
| 脏 section 数 / tick | `PhysicsChunkManager#updateDirtySections` | `sectionsToUpdate.size()` |
| 单次 section 重建耗时 | `PhysicsChunkSection#startAsyncUpdate` | 包住 `buildCollisionShapeAsync(...).await()`（注意在构建线程上） |

**判据**：若「`updateSection` 总耗时 / tick」达到 tick 预算的可见比例（例如 2 ms / 50 ms），则 S1 优先；若 `onBlockUpdated` 的逐方块记账总耗时可见，则 S2/S3 优先。

## 七、与调用方的关系

本文的三条结论对上游调用方（爆炸、大规模破坏类技能、地形编辑指令）有直接影响，建议同步告知：

1. **调小 `setBlock` 的 flags 不会减少地形侧开销**（§四第 4 条）。
2. **整体替换 `LevelChunkSection` 会静默破坏地形同步**，必须自行补 `markDirtySections`（§四第 5 条）。
3. **批量入口（S2）需要调用方配合**：S2 落地之前，调用方无法把整批变更一次交给地形侧；逐方块记账是这条链在当前接口下的必然形态。
